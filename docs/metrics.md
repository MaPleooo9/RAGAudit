# 指标口径说明

这份文档解释每个指标**怎么算**、**什么时候会骗人**。
只看数字不看本文档，很容易得出反向结论。

---

## 为什么用可判定的硬指标

检索层的问题是「该召回哪一条」，不是「话说得好不好」。
所以判定的方式是：评估集给出**期望的层**和**期望的目标**，
检索结果的前 K 条里出现了它，就算命中。

用 LLM 打分可以把两件事混在一起，而且同一个问题跑两次可能得到不同分数。
评测工具本身不可复现，它的结论就没法用来判断别人。

代价是：这套指标**测不出「答案对不对」**，只测「召回对不对」。
要测生成质量，请把这套结果和 RAGAS 之类的工具组合使用。

---

## Hit@K

```
Hit@K = 前 K 条里出现期望结果的问题数 / 总问题数
```

**陷阱**

1. **K 越大越好看，且没有可比性。** 报「Hit@5」时如果对方报的是「Hit@3」，
   两个数不能直接比。本项目默认 K=5，报告里固定写明。
2. **Hit@5 高不代表能用。** 用户只看第一条。Hit@5 96% 而 Hit@1 50% 的系统，
   实际体验极差——正确结果在，但被排到了后面。这两个数要一起看。
3. **n 太小时没有意义。** 10 条题里错 1 条就是 10 个百分点。
   `lint` 会对少于 3 条的分组发出警告。

---

## MRR（Mean Reciprocal Rank）

```
MRR = 平均( 1 / 首个正确结果的排名 )
```

排第 1 得 1.0，排第 2 得 0.5，排第 5 得 0.2，没命中得 0。

**陷阱**：MRR 会掩盖"命中但排在后面"的问题。
两条题，一条排第 1、一条排第 3，MRR = (1 + 0.333)/2 = 0.667，
听起来比实际体验好。所以 MRR 必须和 Hit@1 一起看。

---

## 层准确率@1

Top-1 结果的**层**是否在期望层列表里，不判目标对不对。

它和 Hit@1 是两件事：

- 层错了 → 访问了错误的资料源，这是路由问题
- 层对但目标错 → 在正确的地方排错了，这是排序/实体识别问题

**必须分开统计。** 混在一起时，「层判对但目标排错」和「层判错」看起来一样，
但修的地方完全不同。

> **一个必须知道的边界情况**：层准确率**不应该**低于 Hit@1。
> 命中必然意味着层对。曾经出现过「层准确率 97.2% < Hit@1 98.6%」的倒挂，
> 原因是 `expect_layer` 支持数组 `["l1","l3"]`，而层准确率统计用了 `==` 直接比较，
> 遇数组恒为 False，这几条无论排多准都被判错。
> 现在层判定与命中判定共用同一个函数，从源头消除这类 bug。

## 两套口径，以及「虚高」

「命中」不是自然事实，是**口径选择**。同一份结果换套规则就能从 94% 掉到 89%。

本项目内置两套，报告里**永远并列呈现**：

| 口径 | 规则 | 回答的问题 |
|---|---|---|
| `lenient` | 结果带 `target` → 比 target；不带 → 标题**包含**期望名 | 排第一的是不是跟它**相关**的页面 |
| `strict` | 结果带 `target` → 比 target；不带 → 页面主实体**完全相等** | 排第一的是不是它**本人** |

```
虚高 = lenient.Hit@1 − strict.Hit@1
```

举个具体的例子：知识库里有「玛莲妮亚」本体页和「玛莲妮亚的追忆」物品页。
用户问「玛莲妮亚怎么逃课」，检索返回了物品页——

- `lenient`：标题包含「玛莲妮亚」→ 算命中
- `strict`：页面主实体是「玛莲妮亚的追忆」≠「玛莲妮亚」→ 不算命中

**两套口径都合理**，问题在于只报其中一个且不说明。
对外引用成绩时，必须写清用的是哪套；否则 94% 会被读成"排第一的一定是正确页面"。

> 口径的差异点刻意定在**结果自身有没有 `target` 字段**上，而不是层名上。
> 早期版本按层名分派（给 `l1` 配 contains），换一套层命名之后
> `lenient` 会静默退化成 `strict`——数字没变，含义全变了，人眼看不出来。

## 分组与难度画像

### 为什么必须分组

一份评估集里，问句的难度差异可能巨大。
「玛莲妮亚怎么逃课」和「雪山上那个扔火球的巨人怎么正常打」
测的根本不是同一种能力，混在一起算总分会把结论抹平。

### 自动判定的泄漏等级

不需要人工分组，从题面自动判定：

| 等级 | 判定条件 | 说明 |
|---|---|---|
| `explicit` | 问句直接包含期望目标名 | 实体匹配就能命中，测不出语义检索 |
| `alias` | 问句包含登记过的俗称 | 测的是别名表覆盖度 |
| `partial` | 问句含同名子串（如「龙装大树守卫」之于「大树守卫」） | 实体识别会指向错误目标，比不含实体名更难 |
| `implicit` | 整句不含任何实体名 | **只有这档真正考验语义检索** |

### 同源问句问题

最常见的自欺形式：**写题时就知道知识库里有哪一条**，于是问法自然和库里的措辞对上了。
这类题的通过率必然高，但它测的是"人写的题和机器存的文档像不像"，不是"系统好不好"。

识别特征就是 `explicit` 占比高。`lint` 在显式指名超过 70% 时会警告。

一个诚实的做法：**报告里把每组的泄漏分布也列出来**，让人自己判断这个分数含多少水分。

## 子串误判

用 `in` 做匹配会让「大树守卫」命中「龙装大树守卫」。
实体名之间的包含关系极其常见（「玛莲妮亚」/「玛莲妮亚的追忆」、
「火焰巨人」/「火焰巨人（雪原）」），所以内置规则一律用等号。

反过来，如果问句里同时出现「龙装大树守卫」和「大树守卫」，
按最长匹配取前者——`lint` 会在「问句含比期望目标更长的实体名」时报警，
因为这几乎总是意味着期望值写错了，或者这题注定测不出正确结果。

## 这些指标什么时候会骗人

诚实列出来：

1. **评估集来自同一个人的同一套理解**。再好的指标也只反映这份题的质量。
2. **只覆盖了知识库里"有"的东西**。用户问了库里没有的内容时表现如何，这套指标看不出来。
3. **不测延迟和成本**。Hit@1 100% 但每条查 8 秒的系统，指标上是满分。
4. **不测生成**。检索对了、答案还是编，这套指标不会告诉你。
5. **样本量小时，1 条题就是 10%**。

看到任何单点成绩，先问：几套口径、多少条题、怎么分组、题库怎么来的。
这四个问题答不上来，那个数就不该被引用。
