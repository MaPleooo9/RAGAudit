## 3. 项目简介（300 字版，适合详情页首屏）

> 一个 RAG 系统报出「Hit@1 94.1%」，这行数字本身不构成任何证据。
> 它可能是真的，也可能来自判定口径太松、题库里每题都写着答案、
> 或者命中的是手工维护了三个月的俗称表。
>
> RAGAudit 做的是**审计**：同一个结果按宽/严两套口径各算一遍，差值就是虚高；
> 关掉某个部件再跑一遍，ΔHit@1 就是它的真实贡献；
> 从题面自动判定四条泄漏等级，算出有多少分是靠「问句里写着答案」拿到的；
> 两次运行逐条对齐，区分修好/弄坏/前移/后退，并把**悄悄删掉的难题**单独报出来。
>
> 它不调 LLM 打分，判定完全确定——相同输入永远得到相同输出。
> 纯标准库实现，零运行时依赖，`git clone` 后无需安装即可跑通演示，
> 因此可以直接挂进 CI，在每次提交时回答「这次改动有没有让检索变差」。

## 4. 详细介绍（约 900 字，适合「项目描述」大输入框）

### 4.1 要解决的问题

RAG 评测目前的主流做法是给一个总分。但总分不可审计：它不告诉你这个数是怎么来的。
实践中有四类系统性虚高，且全部发生在**算分环节**而不是**回答问题环节**：

| 虚高来源 | 表现 | 现有工具能否发现 |
|---|---|---|
| 判定口径过松 | 标题里含期望名就算命中 | 否，只报一个口径 |
| 题库泄漏 | 问句直接写着答案实体名，实体匹配即可命中 | 否 |
| 规则抢功 | 分数其实来自别名表/实体置顶，不是语义检索 | 否，需手工改代码对比 |
| 删题涨分 | 悄悄删掉难例，平均分自然上升 | 否，只比总分 |

RAGAS、DeepEval 这类框架解决的是「答案好不好」，量的是忠实度、相关性、幻觉。
它们的判定依赖 LLM-as-judge，换一个裁判模型就换一把尺子，本身也不适合做
「分数可信度」的审计。两者是不同层的问题，不可互相替代。

### 4.2 做了什么

RAGAudit 提供四个命令，对应四个审计动作：

1. **`lint` —— 先查题，再跑分。** 从题面自动判定每条题的实体泄漏等级：
   `explicit`（问句写着答案实体名）/ `alias`（用的是登记过的俗称）/
   `partial`（含同名子串，易指向错误实体）/ `implicit`（整句不含实体名）。
   显式指名超过 70% 时直接警告「这个总分大概率是查词典查出来的」。

2. **`run` —— 双口径并列。** 同一份结果同时按 lenient 与 strict 计算，
   两套口径的差值就是虚高量。报告永远并列呈现，不挑好看的那个报。

3. **`ablate` —— 消融与归因。** 把某个部件关掉再跑一遍，ΔHit@1 即其净贡献；
   **关掉之后反而变好的部件会被单独标出**——负收益模块不该以「还没证明有害」为理由留着。

4. **`diff` —— 逐条回归。** 按题目内容哈希对齐（不是按序号，中间插一条不会让后面全部错位），
   输出 `fixed` / `broke` / `improved` / `worsened` / `added` / `removed` 六类，
   每条退化还给出归因（层路由错还是排序掉了）。`removed` 是审计视角的关键：
   删掉难例同样能让总分上涨。

### 4.3 一个真实审计案例

用已上线的本地 RAG 系统 NaviRAG v1.0.1（8428 条知识库、85 条人工评估集、自报 Hit@1 94.1%）
做了完整审计，评估集与其原文件 SHA-256 完全一致，未改题未删题：

| 审计问题 | 结论 |
|---|---|
| 94.1% 是不是口径撑大的？ | 不是。两套口径差 1.2pp，且这 1.2pp 来自本工具严格口径的误判 |
| 这分是谁挣的？ | 76.5pp 来自实体名硬匹配；关掉后整链只剩 17.6%，纯向量 12.9% |
| 真实泛化水平？ | 「描述提问」组（整句不含实体名）6 条只中 3 条，Hit@1 50% |
| 哪个模块白占位置？ | 术语增强 ΔHit@1 = ±0，MRR 只差 0.004 |
| 哪个部件最脆？ | 手工别名表值 3.5pp，关掉立刻坏 3 条，全是俗称题 |

工具独立算出的五个数字与该系统自评报告**逐位吻合**
（12.9 / 17.6 / 90.6 / 94.1 / MRR 0.951），差异全部来自本工具额外提供的信息。
这既证明审计口径与主流做法等价，也说明审计本身没有引入偏差。

### 4.4 工程取舍

**为什么不用 LLM 打分。** 检索层的问题在「召回哪一条」，不在「话说得好不好」。
用 LLM 当裁判会把两个问题混在一起，且本地小模型打分不可靠、每次跑结果还不一样。
这里只用来可判定的硬指标：期望层 + 期望目标，命中就算对。

**为什么坚持零运行时依赖。** 评估工具本身要是黑盒，它的结论就没法用来判断别人。
纯标准库意味着任何人拿到代码都能逐行核对打分逻辑。

**为什么必须保留逐条结果。** 只留总分的评测撑不起回归测试。
总分掉 0.3 时，你需要知道是哪几条、坏在哪一环。

## 5. 创新点（建议 4 条，每条一句结论 + 一句证据）

1. **把「评测」本身当成被审计对象。** 主流工具输出分数，本项目输出对分数的信任评估：
   双口径差值 = 虚高量，消融差值 = 部件真实贡献，泄漏画像 = 分数的构成比例。

2. **题库泄漏自动画像，无需人工分组。** 从题面自动判定 explicit / alias / partial / implicit
   四档，直接给出「多少分是靠问句里写着答案拿到的」。真实案例中显式指名占 64%，
   而真正考验语义的 implicit 组 Hit@1 只有 50%——这个落差是总分永远显示不出来的。

3. **逐条回归的 `removed` 检测。** 删掉难例同样能让平均分上涨，是评测中最隐蔽的一种操纵。
   本项目按题目内容哈希对齐，把被移除的题目单独列为一条退化项。

4. **确定性判定 + 零依赖，可直接进 CI。** 不调 LLM，相同输入永远相同输出；
   34 个单测、0.01 秒跑完，85 条真实题秒级完成。评测工具要能在每次提交时跑，就不能有 API 账单和网络抖动。

## 10. 评委会问的三个刁钻问题

**Q1：这不就是自己给自己出题吗？**
A：正因为如此才需要审计工具。它的输出不是「我考了 94 分」，而是「这 94 分里 76.5pp 来自实体名、真实语义泛化只有 50%」。
工具的价值在于把出题缺陷量化出来，而不是掩盖它。

**Q2：跟 RAGAS 有什么区别，为什么不直接用？**
A：RAGAS 量答案（忠实度、相关性），依赖 LLM 当裁判，换模型就换尺子。
本项目量分数本身，判定完全确定。两者分层不同，推荐分工是
「RAGAudit 守检索不退化（秒级、进 CI），RAGAS 守答案不退化」。不宣称替代。

**Q3：只支持你那个项目吧？**
A：接入协议是任意 `f(query, k) -> list[结果]`，dict / dataclass / 对象都能自动归一化。
诚实说明：目前只实测过两个检索器（toy 示例与 NaviRAG），
内置的 LangChain / LlamaIndex 适配器还在路线图上，未完成。

## 11. 不要写的话

| 别写 | 原因 |
