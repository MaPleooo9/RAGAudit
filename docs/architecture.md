# 架构

一句话：**评估集、检索器、判定口径三者解耦，任一方可替换。**

这个约束不是洁癖。把「题库长什么样」和「怎么检索」绑在一起，
是所有自制评测脚本最终失去可比性的原因——换了个检索方案，
连题库格式都得改，于是历史数据全部作废。

```
评估集 JSON ──┐
              ├──► run_suite() ──► RunResult ──┬──► render_report() ──► report.md
检索器任意可调用 ─┘                            ├──► diff_runs()      ──► 退化清单
              │                                └──► (存 json，作为下次的基线)
判定口径 Rubric ─┘
```

## 模块

| 模块 | 职责 | 不做什么 |
|---|---|---|
| `schema` | `Case` / `Doc` / `Suite`，加载与归一化 | 不做判定，不做检索 |
| `matchers` | 判定规则与 `Rubric` 组合 | 不算指标 |
| `metrics` | 跑分、汇总、`RunResult` 序列化 | 不决定用什么口径 |
| `ablate` | 变体矩阵、可比子集筛选 | 不实现检索器 |
| `profile` | 难度画像、评估集自检 | 不给分 |
| `diff` | 两次运行逐条对比 | 不重算指标（复用已有排名） |
| `report` | markdown 渲染 | 不做任何计算 |
| `cli` | 参数解析、动态导入 | 不放业务逻辑 |

依赖方向是单向的：`cli → report/ablate/diff/profile → metrics → matchers → schema`。
`schema` 不依赖任何其他模块，这是它能被单独复用的前提。

## 数据流的关键设计

### 1. `Doc` 是唯一的结果归一化入口

不同框架的检索结果形状各异（dict / dataclass / 框架自带 Document 类）。
`Doc.from_any()` 把它们统一成 `layer` / `target` / `title` 三个字段，
原始对象保留在 `raw` 里供自定义规则使用。

字段名不同时用 `field_map` 覆盖，而不是要求用户改自己的代码。

### 2. 判定与指标分离

`matchers` 只回答「这一条算不算命中」，`metrics` 只负责聚合。
好处是**一次运行可以同时产出多套口径的结果**——两套口径共享同一份检索结果，
不需要跑两遍。这也是「双口径并列」成本很低的原因。

### 3. `RunResult` 保留逐条数据

不是只存汇总数字。每条存：排名（按口径分开）、失败归因、前 5 条的概要。

这是 `diff` 能工作的前提。只存总分的评测，事后无法回答
「掉了 0.3 分是哪几条坏掉的」。

### 4. 题目按内容哈希对齐，不按序号

`Case.id = sha1(query)[:12]`。

按序号对齐的后果：在评估集中间插一条题，后面所有题错位，
diff 变成满屏假的「全部变了」。按内容对齐则完全免疫。

### 5. 消融必须在可比子集上做

`ablate(layers=[...])` 会先用 `Suite.only()` 筛子集。

原因：如果某个变体（比如纯规则检索）在某一层上压根无法给出结果，
把它和完整方案放在全集上比，结论是假的——它会在那一层上全部被判错，
看起来"很差"，但这是能力边界而不是设计缺陷。

## 扩展点

| 想做的事 | 怎么接 |
|---|---|
| 自定义判定逻辑 | `@register_rule("name")` + 构造 `Rubric` |
| 接自己的检索器 | 任何 `f(query, k) -> list` |
| 结果字段名不同 | `Doc.from_any(obj, field_map={...})` |
| 新增指标 | 在 `metrics.summarize` 里加，同时更新 `docs/metrics.md` |

## 有意不做的事

- **不做向量库封装**。本项目审计检索，不实现检索。
- **不做 LLM 打分**。不可复现，且会混淆「召回对」和「回答对」两个问题。
- **不做配置文件**。一个命令能跑完的事，不该让人先写 YAML。
